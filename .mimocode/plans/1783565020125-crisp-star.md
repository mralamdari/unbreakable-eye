# Fix: Exit code 135 (SIGBUS) when navigating monitor page

## Root cause

When you navigate away from the monitor page and come back, the app triggers a pipeline restart (`cameras_dirty=True`). During teardown, the executor thread unmaps shared memory (`munmap()`) while the event loop thread is still reading from it in `generate()`. This causes SIGBUS (exit code 135).

**The race:**
1. `generate()` creates a numpy view on `output_shm.buf` (mmap'd memory)
2. `_cleanup_shm()` calls `shm.close()` → `munmap()` from a different thread
3. `munmap()` unmaps memory for the entire process
4. `generate()` hits unmapped memory → SIGBUS

## Plan

### Fix 1: Add `shm_size` to docker-compose.yml

**File:** `docker-compose.yml`

Add `shm_size: 2g` to the fastapi service. Docker's default 64MB `/dev/shm` is insufficient for 2+ cameras (each camera uses ~33MB of SHM).

```yaml
  fastapi:
    ...
    shm_size: '2g'
```

### Fix 2: Add proper shutdown signal before cleanup

**File:** `src/web/main.py`

Add a `threading.Event` to signal all `generate()` coroutines to stop before teardown begins. This prevents the race between teardown and MJPEG streaming.

### Fix 3: Stop shared embedder during teardown

**File:** `src/web/main.py`

Add `_stop_shared_embedder()` call in `_teardown_sync()` — currently it's only called during app shutdown, leaking zombie processes on restarts.

### Fix 4: Add SIGKILL fallback to batched detector stop

**File:** `src/web/main.py`

Add `kill()` fallback after `terminate()` + `join()` in `_stop_batched_detector()`, matching the pattern used for per-camera workers.

## Files to modify

1. `docker-compose.yml` — add `shm_size: '2g'`
2. `src/web/main.py` — add shutdown signal, stop shared embedder in teardown, add SIGKILL fallback

## Verification

```bash
docker compose up -d --build
# Login, navigate to monitor, navigate away, navigate back
# Should NOT get exit code 135 or 504 error
docker compose logs fastapi | grep -E "135|SIGBUS|shutdown"
```
